System Architecture

General Architecture of the Olive Oil Sample Evaluation System

The application is built on a simple 3-tier client-server architecture: a Flutter mobile application (presentation tier) communicates through a REST API with a Django backend (application / logic tier), which stores its data in a PostgreSQL database (data tier).

Figure: 3-tier client-server architecture of the Al Jazeera STCA olive oil sample evaluation system.

Presentation Tier

Flutter Mobile App

The interface used by every role. It shows only the screens and actions allowed for the connected user and sends all requests to the backend through the REST API.

Application / Logic Tier

Django REST Backend

Handles login and JWT tokens, checks role-based permissions, applies the business rules of each module, and returns structured JSON responses.

Data Tier

PostgreSQL + Media

PostgreSQL stores the structured data (users, samples, evaluations, analyses, purchases). Media storage keeps uploaded files such as bottle-label photos.

How It Works

A user opens the Flutter mobile application and signs in. Every screen sends its requests to the Django backend through the REST API, exchanging data in JSON format over HTTP. A JWT token, stored securely on the device, accompanies each request so the backend can identify the user and apply the permissions of their role.

The backend executes the requested action — for example, registering a sample, recording an evaluation, reading a bottle label, or confirming a purchase — then reads from or writes to the PostgreSQL database and returns the result. Uploaded photos are kept in a dedicated media storage area rather than inside the database. The map of Tunisian delegations is shipped with the application as a local asset, so it does not require a network call.

Why This Architecture

  • It cleanly separates the mobile interface from the backend logic, which keeps the project easy to understand, test, and maintain.
  • A single REST API serves all five roles; access stays controlled through authentication and role-based permissions.
  • Business rules live in the Django backend, not scattered across the mobile screens, so the same rule is enforced for everyone.
  • PostgreSQL is well suited to the structured, related data of this domain (users, samples, evaluations, analyses, purchases).
  • It stays simple and realistic for the scope of this project — no microservices, no API gateway, no extra layers that would add complexity without value.

Quick Answers (for the defense)

  • What architecture is it? A 3-tier client-server architecture: presentation (Flutter), application/logic (Django REST), and data (PostgreSQL).
  • How does the app talk to the server? Through a REST API — HTTP requests with JSON data, secured by a JWT token.
  • How are the different users separated? By role-based permissions checked in the backend; each user only reaches their own features.
  • Where are photos stored? In media storage on the server; the database keeps only the reference, not the file itself.
  • Why not microservices? The project is a single, well-defined application; one backend is simpler, faster to build, and enough for the expected load.
