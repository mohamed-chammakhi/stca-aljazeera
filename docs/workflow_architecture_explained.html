Whole workflow explained

How data moves through your Flutter + Django project

This page explains the full workflow in one beginner-friendly map. It uses your real project structure: Flutter screens call services, services call ApiClient, ApiClient sends HTTP requests, Django validates and saves, then the response comes back as a Flutter object.

The golden rule: the screen never saves directly to the database.
Screen -> Service -> ApiClient -> Django API -> Database -> Django response -> ApiClient -> Service -> Model object -> Screen.

The full workflow, step by step

1

The screen starts the action

The screen is the place the user sees. It should not know how HTTP works and it should not know how the database works. It only reacts to the user and asks the service to do the work.

Example files

lib/main.dart

Login screen calls authService.login().

lib/2_collecteur/mes_echantillons/mes_echantillons_page.dart

Collector sample screen calls _service.createEchantillon().

What the screen should do

final saved = await _service.createEchantillon(sample);

setState(() {
  _echantillons.insert(0, saved);
});
Screen = "The user clicked this. Please save/load something for me."
2

The service prepares feature data

The service knows the meaning of the feature. For collector samples, it knows Django expects fields like reference_bouteille, code_fournisseur, and statut_collecteur. It prepares a Dart Map with those field names.

Example file

lib/2_collecteur/mes_echantillons/services/echantillon_collecteur_service.dart

This is where _toDjangoMap() prepares the data for Django.

Important idea

final response = await apiClient.post(
  '/api/echantillons/',
  _toDjangoMap(e),
);
Flutter object EchantillonCollecteur( referenceBouteille: "B-1207", variete: "Chemlali" )
Dart Map for Django { "reference_bouteille": "B-1207", "variete": "Chemlali" }
Still not JSON text This is still a Dart Map. It only looks like JSON because the field names are written as strings.
Service = "I know what this feature is and how Django wants the data named."
3

The ApiClient does the HTTP work

ApiClient does not care if the data is a sample, a user, a notification, or a lab analysis. It only knows how to send HTTP requests correctly.

Example file

lib/core/api_client.dart

This is where headers are created, JSON is encoded, and HTTP is sent.

Important idea

final headers = await _headers();

final response = await http.post(
  _uri(path),
  headers: headers,
  body: jsonEncode(body),
);
Path from service "/api/echantillons/"
Body from service Map<String, dynamic> body
Real JSON moment jsonEncode(body)
ApiClient = "Give me a path and a Dart Map. I will add headers, turn the Map into JSON text, and send the request."
4

The headers carry the login token

When the user is logged in, ApiClient adds the access token to the request. This is how Django knows who is making the request.

Example file

lib/core/api_client.dart

Look for the _headers() method.

Important idea

return {
  'Content-Type': 'application/json',
  if (token != null)
    'Authorization': 'Bearer $token',
};
Header = "Here is the user's login badge. Django can use it to identify the user."
5

Django receives the request

Django receives the URL, the headers, and the JSON body. Then it decides: is the user allowed? Is the data valid? Which database table should be used?

URL routing

backend_new/*/urls.py

Chooses which Django view handles the request.

View / ViewSet

backend_new/*/views.py

Applies permissions and business actions.

Serializer

backend_new/*/serializers.py

Validates data and converts JSON into Django objects.

Django = "I check permissions, validate the data, run business rules, and save/read from the database."
6

The database stores or returns rows

Flutter never touches PostgreSQL. Only Django talks to the database through its models and ORM.

Backend model files

backend_new/users/models.py
backend_new/echantillons/models.py
backend_new/evaluations/models.py
backend_new/analyses/models.py

What gets stored

  • Users and roles
  • Samples and suppliers
  • Organoleptic evaluations
  • Laboratory analyses
  • Notifications and sessions
Database = "I store the final truth, but Django is the gatekeeper."
7

Django sends JSON back

After saving or loading data, Django sends a JSON response. For example, after creating a sample, Django sends the saved sample with its real id, number, date, status, and collector information.

Flutter sent { "reference_bouteille": "B-1207", "variete": "Chemlali" }
Django saved Adds generated values. id numero date_ajout collecteur
Django returns { "id": "uuid", "numero": "2026/0042", "reference_bouteille": "B-1207" }
Response = "Here is the official saved object from the server."
8

ApiClient decodes the response

HTTP responses arrive as text. ApiClient turns the JSON text back into a Dart Map so the service can use it.

Example file

lib/core/api_client.dart

Every get/post/patch method ends by decoding the response.

Important idea

_assertSuccess(response);

return jsonDecode(response.body)
  as Map<String, dynamic>;
ApiClient return trip = "The server sent JSON text. I turned it into a Dart Map."
9

The service converts the response into a model object

The service takes the response Map and calls fromJson(). This creates a real Flutter object that the screen can display.

Example service

lib/2_collecteur/mes_echantillons/services/echantillon_collecteur_service.dart

The service receives the response and returns an EchantillonCollecteur.

Important idea

return EchantillonCollecteur.fromJson(
  _toFlutterMap(response),
);
fromJson = "Take the Map that came from Django and rebuild a Flutter object."
10

The screen updates

The screen receives the saved object from the service. Then it updates its local list using setState(), so the user sees the new data.

Example page

lib/2_collecteur/mes_echantillons/mes_echantillons_page.dart

The saved sample is inserted into the visible list.

Important idea

setState(() {
  _echantillons.insert(0, saved);
});
Screen return trip = "I got the saved object back. Now I show it."

Two important workflows in your project

A

Authentication workflow

Login follows the same architecture, but the response is tokens first, then the user profile.

Forward LoginPage -> AuthService -> ApiClient.login() -> POST /api/auth/login/
Response { "access": "...", "refresh": "..." }
Then GET /api/users/me/ -> UserProfile.fromJson() -> _destinationForRole()
B

Collector sample creation workflow

Adding a sample follows the full screen-service-api-backend-database round trip.

Forward MesEchantillonsPage -> EchantillonCollecteurService -> apiClient.post() -> POST /api/echantillons/
Django views.py serializers.py models.py PostgreSQL
Back jsonDecode() -> EchantillonCollecteur.fromJson() -> setState()

If an error happens

!

The error also travels back through the same path

If Django refuses the request, ApiClient catches the bad status code and throws an ApiException. The service/page can show a friendly error message.

Backend error example

{
  "detail": "Not allowed"
}

Flutter idea

_assertSuccess(response);

// if statusCode >= 400:
throw ApiException(...);
Error flow = "Django says no, ApiClient turns it into an exception, UI shows the message."

The architecture in one sentence

Your project uses a client-server layered architecture: Flutter screens call services, services prepare feature data, ApiClient performs HTTP and token work, Django validates and applies business rules, PostgreSQL stores the data, and the response is converted back into Flutter model objects for the screen.
