L'architecture de votre app,
expliquée simplement

Une appli mobile Flutter qui parle à un serveur Django. Ce n'est pas du MVC — c'est une architecture en couches, 3-tiers. Voici la même idée, sans jargon.

// LA RÉPONSE COURTE

Est-ce du MVC ?

Non

Votre projet utilise une architecture client-serveur 3-tiers, avec côté mobile une architecture en couches (Modèle · Service · Vue). Le MVC a un « Contrôleur » au centre ; ici c'est la couche Service qui joue ce rôle, et l'interface se met à jour toute seule (setState).

// L'IMAGE MENTALE

L'analogie du restaurant

Le moyen le plus simple de retenir une archi 3-tiers.

Restaurant = votre système

🍽️ La salle = l'app Flutter

Le client voit les menus, passe commande. Il ne sait pas comment on cuisine.

👨‍🍳 La cuisine = le serveur Django

Reçoit les commandes (requêtes), applique les règles (recettes), prépare le plat.

🧊 Le frigo/garde-manger = la base PostgreSQL

Stocke tous les ingrédients (les données). Seule la cuisine y touche.

Le serveur (l'API) fait le va-et-vient entre la salle et la cuisine. C'est exactement vos 3 tiers.

// VUE D'ENSEMBLE

Les 3 tiers (les 3 grandes briques)

Chaque brique a un seul travail. Elles communiquent en JSON via HTTP.

1

Application Flutter

Tier présentation · le client mobile

Ce que l'utilisateur voit et touche : écrans des 4 rôles (Directeur, Collecteur, Dégustateur, Labo). Affiche les données, capte les actions.

requête HTTP / JSON ⇅ réponse JSON
2

API Django REST

Tier logique métier · le serveur

Le cerveau : vérifie les droits, applique les règles métier (états d'un échantillon, validations), prépare les données.

requête SQL ⇅ lignes de données
3

Base PostgreSQL

Tier données · le stockage

Conserve tout durablement : utilisateurs, échantillons, évaluations, analyses. Seul Django y accède.

// ZOOM CÔTÉ MOBILE

Les 3 couches dans Flutter

Chaque fonctionnalité (ex : gestion_echantillons) est découpée en 3 dossiers. C'est le cœur à montrer au jury.

couche 01

Vue

widgets/ + *_page.dart

L'interface uniquement. Affiche et capte les clics. Ne calcule rien, ne parle pas à internet.

couche 02

Service

services/

Le chef d'orchestre. Appelle l'API, applique la logique, transforme les données pour la vue.

couche 03

Modèle

models/

La forme des données. Classes avec fromJson() / toJson() pour passer du JSON aux objets.

// EN MOUVEMENT

Que se passe-t-il quand on ouvre une liste ?

Exemple concret : le dégustateur ouvre « Mes échantillons ».

1Vue — l'écran s'affiche, demande les données au Service
2Service — envoie une requête HTTP GET /echantillons/ à Django
3Django — vérifie le token, demande les lignes à PostgreSQL
4PostgreSQL — renvoie les données ; Django les transforme en JSON
5Service — reçoit le JSON, le convertit en objets Modèle
6Vue — setState() redessine la liste à l'écran ✓
// LE PIÈGE À ÉVITER

Pourquoi ce n'est pas du MVC

MVC classique

  • Un Contrôleur central reçoit l'action
  • Il décide quoi faire et met à jour la Vue
  • La Vue est « passive »

Votre projet (MVS en couches)

  • Pas de Contrôleur : la couche Service coordonne
  • La Vue se met à jour seule via setState()
  • Côté Django : patron MVT adapté en API REST (Modèle · Serializer · Vue)
// À RECOPIER DANS LE RAPPORT

La phrase pour le jury

Paragraphe « Architecture » — prêt à l'emploi

L'application repose sur une architecture client-serveur 3-tiers. Le client mobile, développé avec Flutter, suit une architecture en couches orientée fonctionnalités : chaque module métier est découpé en trois couches — Modèle, Service et Vue. Le serveur, développé avec Django REST Framework, suit le patron MVT adapté en API REST. La communication s'effectue via des requêtes HTTP/REST échangeant des données au format JSON.
