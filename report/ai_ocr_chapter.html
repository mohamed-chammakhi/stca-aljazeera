Final Year Project — Chapter

Artificial Intelligence in the Sample Evaluation Workflow
OCR for the Collector and the Laboratory

Two on-premise OCR pipelines that accelerate data entry while keeping every image and every model inside the company network.

1. Context and Constraints

The Al Jazeera STCA sample evaluation system handles two situations in which an operator must transcribe information from a physical artifact into the application:

  • A collector in the field photographs a small plastic bottle on which three things are written with a marker — the quantity, the cistern number, and the supplier or "huilerie" name.
  • A laboratory technician at the company photographs a printed report that contains the chemical analysis values of an olive oil sample.

Both situations are good candidates for OCR-assisted data entry. The company, however, imposes a hard rule: no image and no extracted text may leave the company premises. This rules out every cloud-based OCR service (Google Vision, AWS Textract, Azure Document Intelligence, Gemini, Claude, GPT). Every model must run locally on the company's own server.

Design stance. Both pipelines are built around a human-in-the-loop philosophy: the AI accelerates data entry by pre-filling fields; the user remains responsible for confirming every saved value. The AI is presented as an assistant, never as an authority — a position that fits both the technical reality of OCR accuracy and the financial weight of the downstream decisions.

2. OCR for the Collector — Reading Handwritten Bottle Labels

2.1 Nature of the Problem

The collector writes by hand on small plastic bottles with a marker. The three values that need to be extracted are short and follow no fixed template:

  • Quantité — a number, optionally with a decimal, followed by the unit T (e.g. 8T, 10.5T).
  • Citerne — an arbitrary letter-and-digit code (e.g. c2, aa11, p1).
  • Fournisseur / Huilerie — a personal or business name (e.g. issa rached).

The technical difficulty is high: curved and shiny plastic surface, glare, variable lighting in the field, freehand cursive marker, and the fact that the cistern and quantity codes are arbitrary strings and therefore not in any dictionary.

2.2 Technique

The recognition stage uses a CRNN + CTC model (Convolutional Recurrent Neural Network with Connectionist Temporal Classification). This family of models recognizes text character by character with no built-in language model, which is exactly the property we need: handwritten codes must be read literally and not "corrected" into dictionary words.

A language-biased decoder, such as the transformer head used in TrOCR, was evaluated and rejected for this pipeline. On ambiguous strokes it tends to convert a code like aa11 into a French-looking word, which corrupts the cistern field and ultimately the sample traceability.

2.3 Tool

The implementation uses EasyOCR (Apache 2.0 license), which combines a CRAFT text detector with a CRNN + CTC recognizer and supports French and English in a single model. EasyOCR runs entirely offline once its model files have been downloaded the first time. It accepts a character allowlist, which we use to lock down the recognition of structured fields.

2.4 Post-processing pipeline

  1. The collector takes or selects a photo from the Flutter application; the image is uploaded to the backend.
  2. EasyOCR returns every text region detected on the photo, with a recognition confidence for each one.
  3. A classification step assigns each detected string to one of the three target fields using its shape: a number ending in T is the quantity, a short alphanumeric token is the cistern, and the longest mostly-alphabetic string is the supplier name.
  4. The supplier name is matched against the existing Fournisseur list using case-insensitive edit-distance similarity. If a close match is found, the existing supplier is reused; otherwise a new supplier is created with a clean auto-generated code of the form F-NNNN.
  5. The application pre-fills the registration form. Fields with low OCR confidence are visually marked so the collector double-checks them before saving.

3. OCR for the Laboratory — Reading Printed Analysis Reports

3.1 Nature of the Problem

The laboratory technician works with printed reports. Each report contains a small set of numeric values that drive a purchase decision: acidité, indice de peroxyde, K232, K270, ΔK, humidité and impuretés. The accuracy requirement is much stricter than for the collector: a wrong value here may corrupt a purchase decision of significant financial value.

3.2 Technique

The pipeline uses deterministic OCR plus label-based numeric extraction. The OCR engine produces the raw text exactly as it appears on the page; a post-processing step then locates each chemical label (with French and abbreviated synonyms) and captures the first decimal number that follows it. Every extracted value is finally checked against an expected physical range.

A generative vision-language model (such as a locally hosted Qwen-VL or Llama-Vision) was evaluated and rejected for this pipeline. A generative model can produce a confident but incorrect numeric value when the image is ambiguous (a phenomenon known as hallucination). For a chemical value that feeds a purchase decision, this risk is unacceptable. A deterministic OCR + validation pipeline is auditable: either the value is read from the document or it is flagged as missing for the technician to confirm.

3.3 Tool

The implementation uses PaddleOCR (Apache 2.0 license), which provides a detection + recognition pipeline tuned for printed documents and supports a French language mode. PaddleOCR runs entirely offline once its model files have been downloaded for the first time.

3.4 Post-processing pipeline

  1. The technician takes or selects a photo of the report; the image is uploaded to the backend.
  2. PaddleOCR returns every recognized text line.
  3. For each of the seven chemical fields, the system searches for its label (and known abbreviated forms) and extracts the first decimal number that follows the label.
  4. Each value is validated against a plausible physical range. Any value out of range, or any field that was not found at all, is attached to a _warnings list returned to the application.
  5. The Flutter form is pre-filled. Fields flagged in the warnings are highlighted in orange so the technician can confirm or edit them manually before submitting the analysis.

4. Shared Architecture

Both pipelines share the same architectural pattern: a Flutter client captures the image, a Django REST endpoint receives it, the appropriate offline OCR engine processes it on the on-premise server, and a structured response feeds an editable form that the user confirms.

6. Justification of the Design Choices

The choices presented above are the result of explicit trade-offs. The most important ones, summarized for the defense:

  • Two engines instead of one. EasyOCR and PaddleOCR target different problem classes — handwritten arbitrary codes versus printed structured documents. Forcing one engine to do both would weaken both. Using each engine for the situation it is best at gives stronger results overall.
  • No generative AI. Generative vision-language models are powerful but they can produce confident yet wrong outputs. For the laboratory pipeline, where a wrong number drives a wrong purchase, this risk is not acceptable. For the collector pipeline, a language-model-biased recognizer would "correct" handwritten codes into real words. In both cases a deterministic, character-level approach is more honest.
  • No cloud. Every model and every image stays on the company's own server. This satisfies the company's data-residency rule absolutely, with no exception and no fallback path to a cloud service.
  • Human-in-the-loop is a feature, not a workaround. OCR on real-world inputs is never perfect. The system explicitly marks its own uncertainty (confidence scores for handwritten fields, range warnings for chemical values) so the user can focus their verification effort on the values that need it. This makes the system safer and more transparent than one that silently commits whatever the model produced.
