Chapter 2
Agile Project Planning

2.1 Introduction

The Al Jazeera STCA mobile platform is developed following the Scrum agile framework, chosen for its iterative nature and its suitability for projects where requirements must be validated progressively through working software. The project spans three months and is organized into six sprints of two weeks each (ten working days), each delivering a set of functional, tested, and integrated features.

The platform serves five distinct roles — Administrator, Collector, Panel Member, Panel Evaluation Supervisor, and Laboratory Technician — whose workflows are interdependent. The sprints are sequenced to respect the data pipeline: authentication and user management lay the foundation, sample collection and registration follow, sensory evaluation pipelines are then built upon received samples, and finally laboratory analysis and administrative oversight complete the cycle.

2.2 Project Actors

The following use case diagram presents all five roles and their relationships to the system modules. Every role inherits from the base User actor, sharing authentication, profile management, and notifications. Role-specific feature access is governed by server-side permission classes enforced through the Django REST Framework.

Use Case: US-01 — Authentication & Session Management

Use CaseAuthentication & Session Management
Actor(s)All Users (Administrator, Collector, Panel Member, Panel Evaluation Supervisor, Laboratory Technician)
PreconditionsThe user has a registered account. The Django backend is reachable.
Main Scenario
  1. The user opens the application and is presented with the login screen.
  2. The user enters their email address and password and submits.
  3. The backend validates credentials and returns a JWT access token and refresh token.
  4. The application stores tokens securely using flutter_secure_storage.
  5. The user is routed to their role-specific home page based on the decoded role claim.
Alternative ScenarioIf credentials are invalid, the server returns HTTP 401 and the application displays an error message. If the access token has expired, the refresh token is used to obtain a new access token silently.
PostconditionsThe user is authenticated and has access to their role-specific workspace. All subsequent API requests include the Bearer token in the Authorization header.

Use Case: US-02 — Profile Management

Use CaseProfile Management
Actor(s)All Users
PreconditionsThe user is authenticated.
Main Scenario
  1. The user navigates to their profile page via the drawer.
  2. The current profile data (name, family name, email, phone, photo) is fetched from the API and displayed.
  3. The user edits one or more fields and optionally uploads a new profile photo.
  4. The user saves changes; the application sends a PATCH request to the API.
  5. A confirmation message is shown and the updated data is reflected immediately.
Alternative ScenarioIf the user wants to change their password, they enter the current password and the new password twice. Validation errors (mismatch, weak password) are shown inline. The user may also log out from the profile page, which clears all stored tokens.
PostconditionsThe user's profile is updated in the database and the updated information is reflected throughout the application.

Use Case: US-10 — User Management

Use CaseUser Management
Actor(s)Administrator
PreconditionsThe Administrator is authenticated. They have the IsAdministrator permission class granted on the backend.
Main Scenario
  1. The Administrator opens the User Management page from the drawer.
  2. The list of all registered users is fetched and displayed as cards with role badges, name, email, and phone.
  3. The Administrator taps the create button, fills in the new user's role, full name, email, phone, and a temporary password.
  4. The application posts the new user to the API; a success confirmation dialog is shown with the generated credentials.
  5. To deactivate or delete a user, the Administrator selects the user card and chooses the corresponding action from the options menu.
Alternative ScenarioIf the email address is already registered, the API returns a validation error and the Administrator is prompted to use a different address. Deactivating (not deleting) a user preserves all their data while preventing login.
PostconditionsThe new user can log in with their credentials. Deactivated users are blocked from authentication. Deleted users are removed from all lists.

Use Case: US-12 — Sample Management

Use CaseSample Registration & Field Management
Actor(s)Collector
PreconditionsThe Collector is authenticated. Network connectivity may be unavailable (offline mode supported).
Main Scenario
  1. The Collector taps the FAB on the Mes Échantillons page to open the sample registration form.
  2. The Collector optionally photographs the bottle label; the application sends the image to Gemini Vision API, which extracts fields (supplier code, variety, bottle reference, origin) and auto-fills the form.
  3. The Collector reviews, adjusts, and completes remaining fields (quantity, seal state, expected arrival date).
  4. Upon save, the server auto-assigns a sequential numéro (format YYYY/NNNN); the sample is created in the Réceptionné state.
  5. If offline, the record is queued locally with a temporary UUID and synced automatically when connectivity is restored.
Alternative ScenarioTo register multiple bottles from the same supplier, the Collector adds bottle rows within the same form. Once a sample is physically received (recuPhysiquement = true), subsequent edits are tracked in the edit history.
PostconditionsThe sample record exists in the system and is visible to the Administrator, Panel Member, and Panel Evaluation Supervisor.

Use Case: US-13 — Geographic Map Consultation

Use CaseGeographic Delegation Map
Actor(s)Collector
PreconditionsThe Collector is authenticated. The delegations.geojson asset is bundled with the application.
Main Scenario
  1. The Collector opens the Carte page from the drawer.
  2. The GeoService singleton parses the GeoJSON file and renders all Tunisian delegations as polygons on a flutter_map tile layer.
  3. Delegations already visited (linked to registered samples) are highlighted in olive green.
  4. Unvisited delegations remain neutral, helping the Collector identify uncovered zones.
  5. The Collector pans and zooms the map to plan upcoming collection routes.
Alternative ScenarioIf no samples have been registered yet, all delegations appear in the neutral (unvisited) state.
PostconditionsThe Collector has a clear geographic overview of coverage and can make informed decisions about which regions to visit next.

Use CasePersonal Dashboard
Actor(s)Panel Member
PreconditionsThe Panel Member is authenticated and at least one sample has been physically received.
Main Scenario

Use Case: US-17 — Sensory Evaluation Management

Use CaseSensory Evaluation Submission
Actor(s)Panel Member
PreconditionsThe actor is authenticated. The target sample has recuPhysiquement = true. The actor has not yet submitted an evaluation for this sample.
Main Scenario
  1. The actor opens the Évaluation des Échantillons page; samples are listed with per-actor state badges (En attente / En cours / Soumis).
  2. The actor selects a sample in En attente state and opens the evaluation form.
  3. The form collects olfactory attributes, gustatory attributes, general impression, and a classification vote (Extra Vierge / Vierge / Lampante).
  4. The actor may save a partial evaluation (transitions to En cours) and resume later.
  5. On final submission, the state transitions to Soumis and the form becomes read-only. A Django signal notifies the Supervisor and Administrator.
Alternative ScenarioIf the actor attempts to edit a Soumis evaluation, the form opens in read-only mode with a "Submitted" banner.
PostconditionsThe evaluation is persisted. The Administrator and Supervisor are notified. If all active panel members have now submitted, an additional "all evaluations complete" notification is sent.

Use Case: US-23 — Cross-Panel Evaluation Supervision

Use CaseCross-Panel Evaluation Overview
Actor(s)Panel Evaluation Supervisor (exclusive)
PreconditionsThe Supervisor is authenticated. At least one panel member has submitted an evaluation.
Main Scenario
  1. The Supervisor opens the Vue d'ensemble des Évaluations page; samples are listed with a summary of submitted evaluations.
  2. The Supervisor expands a sample card to reveal each panel member's classification and individual attribute scores side-by-side.
  3. If the score deviation of any taster exceeds 1.5 from the panel average (requiring ≥3 evaluations), a Divergence warning badge is automatically displayed on that sample.

Use Case: US-25 — Laboratory Analysis Management

Use CaseLaboratory Analysis Management
Actor(s)Laboratory Technician
PreconditionsThe Laboratory Technician is authenticated. At least one sample has recuPhysiquement = true.
Main Scenario
  1. The Technician opens the Échantillons / Analyses page; only physically received samples are shown, grouped by analysis state (En attente / En cours / Soumis).
  2. The Technician selects a sample in En attente and chooses either: (a) Scan mode — photographs the physical paper analysis report; the AI extracts chemical parameter values and pre-fills the form fields for review; or (b) Manual mode — enters all chemical parameters directly into the form.
  3. The Technician reviews the pre-filled values (in scan mode), makes corrections if needed, and saves. The analysis transitions to En cours.
  4. Once all parameters are confirmed, the Technician submits the analysis (Soumis). A Django signal notifies the Administrator and Supervisor.
  5. The Technician can export the completed analysis record.
Alternative ScenarioIf the scanned document is illegible or partially recognized, the Technician switches to manual mode and completes the form by hand. The original paper photo is preserved alongside the digital analysis record.
PostconditionsThe analysis is in the Soumis state and visible in read-only mode to the Panel Member, Panel Evaluation Supervisor, and Administrator.

Use Case: US-24 — Notification Management (Laboratory Technician)

Use CaseNotification Centre
Actor(s)Laboratory Technician
PreconditionsThe Laboratory Technician is authenticated.
Main Scenario
  1. The Technician sees an unread count badge on the notification bell icon in the app bar.
  2. The Technician taps the bell and is navigated to the Notification Centre page.
  3. Notifications are displayed in reverse-chronological order; the primary notification type is Échantillon reçu, alerting the Technician that a new sample is awaiting chemical analysis.
  4. Tapping a notification marks it as read and navigates directly to the relevant sample in the analysis page.
Alternative ScenarioThe Technician can mark all notifications as read at once. If no unread notifications exist, the badge is hidden.
PostconditionsThe unread badge count is updated. The notification is marked as read in the database.
